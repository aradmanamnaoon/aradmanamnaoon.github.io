A Hugging Face Gradient Accumulation Bug Almost Ruined My 19-Hour NLLB Training Run

I was fine-tuning NLLB-200 for English↔Persian translation when training loss climbed to nearly 10× validation loss. The data was fine. The real problem was hiding inside the training loop.

By Aradman Amnaoon October 2, 2026 ~8 min read
Quick answer In my NLLB-200 run, training loss scaled almost linearly with gradient_accumulation_steps: 3.24 at accumulation 1, 6.87 at 2, 13.30 at 4, and 25.92 at 8. The issue was tied to Hugging Face Trainer's loss-normalization path for a model that did not use num_items_in_batch. Setting trainer.model_accepts_loss_kwargs = False brought training loss from 24.26 to 3.03 and the gradient norm from 0.234 to 0.030.

I expected a long training run to fail in one of the obvious ways: an out-of-memory error, corrupted data, a bad checkpoint, or maybe a learning rate that was obviously too aggressive.

Instead, everything looked normal.

I was fine-tuning NLLB-200 for English↔Persian translation. The dataset had been cleaned. Loss appeared to be moving. Checkpoints were being saved. Nothing had crashed.

Then I ran a sanity check.

Training loss 24.26
Validation loss 2.55

A gap that large didn't look like ordinary noise. My first thought was overfitting, but the scale of the difference bothered me. More importantly, it didn't fit what I was seeing elsewhere in the run.

That was the point where a 19-hour training job turned into a debugging session.

I spent four hours debugging the wrong things

My first assumption was that I had made a mistake. That is usually the useful assumption in machine learning: before blaming a framework, check your own pipeline.

I worked through the explanations that seemed most plausible:

  • Bad tokenization? I checked it. The tokenized examples looked clean.
  • Incorrect label masking? I checked that too. It was correct.
  • Learning rate too high? I divided it by eight. The strange loss relationship remained.
  • Mixed sequence lengths? I checked for a correlation. There wasn't one.

At that point I had spent hours changing things without explaining the actual symptom.

The breakthrough came when I stopped asking, “Which part of my dataset is broken?” and started asking, “What variable makes this number change?”

The controlled experiment that exposed the problem

I kept the model and data fixed and changed only one parameter: gradient_accumulation_steps.

If the problem came from the data, tokenization, or random batch composition, I would not expect the reported loss to scale cleanly with that single training parameter.

But that is almost exactly what happened.

That pattern was the clue I needed. At accumulation 8, the loss was almost exactly eight times the baseline.

It was difficult to explain that as a property of the translation data. It pointed directly at how the training loop was handling gradient accumulation and loss normalization.

Why gradient accumulation mattered

Gradient accumulation is a way to simulate a larger effective batch without fitting that entire batch in memory at once. Instead of updating the model after every mini-batch, training accumulates gradients over several mini-batches and then performs an optimizer step.

Conceptually, changing the number of accumulation steps should not make the same underlying loss suddenly become 2×, 4×, or 8× larger simply because I chose a different accumulation setting.

That is why the sweep was so useful. The relationship was too clean.

The Hugging Face Trainer loss-normalization issue

The issue I traced this to involved Hugging Face Trainer, gradient accumulation, and the handling of num_items_in_batch.

In the training setup I was using, the model did not use num_items_in_batch in the way Trainer's loss-normalization path expected. The result was incorrect loss scaling during gradient accumulation.

This was not just a cosmetic problem in a progress bar. In my run, the gradient norm changed dramatically as well, which meant the optimization behavior itself was affected.

Important current-context note: Hugging Face's current Trainer documentation explicitly says that when a loss does not use num_items_in_batch, model_accepts_loss_kwargs should be set to False; otherwise loss calculation can be inaccurate during gradient accumulation. Framework behavior changes over time, so check the documentation for the Transformers version you are actually using.

The one-line fix

For my run, the fix was:

trainer.model_accepts_loss_kwargs = False

After making that change, the numbers finally made sense.

Training loss was now in the same neighborhood as the validation loss. The gradient norm fell from 0.234 to 0.030.

Most importantly, I finally had an explanation that matched the evidence.

Why this bug was easy to miss

The frustrating part was that the training run did not look broken in the usual sense.

There was no exception telling me that loss normalization was wrong. There was no giant red warning saying that gradient accumulation was changing the scale of my optimization. The pipeline continued to train and save checkpoints.

High-level training abstractions are useful precisely because they hide a lot of machinery. But this experience reminded me that the machinery still matters.

When the numbers violate your expectations, it is worth temporarily treating the framework itself as another component to test—not immediately as the component to blame, but as something that can be isolated experimentally.

What I would do differently now

1. Treat large train/validation disagreements as a debugging signal

A large gap can have many causes, including genuine overfitting. But I learned not to automatically interpret every loss gap as a property of the model or dataset.

If training and validation losses disagree dramatically, I now want to know whether they are actually being calculated on comparable scales before drawing conclusions from them.

2. Sweep the parameter you suspect

This was the most valuable debugging lesson from the entire experience.

I spent hours checking individual hypotheses. The experiment that actually exposed the problem was simpler: change one parameter through a small range and observe the relationship.

Testing accumulation values of 1, 2, 4, and 8 turned a vague suspicion into an obvious pattern.

3. Run a small controlled job before the expensive one

A long training run is a bad place to discover a basic scaling problem.

Before committing to a large run, I would now reproduce the full training configuration on a small subset, compare training and evaluation behavior, vary the important batching parameters, and inspect a few actual model outputs.

4. Don't trust a metric just because the framework printed it

Metrics are outputs of code. They are not ground truth.

If a value behaves strangely, test how it responds to controlled changes. That is often more informative than staring at the number itself.

The bigger lesson: abstractions don't remove the need to understand training

I still like high-level tools. I am not interested in rewriting an entire training loop every time I fine-tune a model.

But there is a difference between using an abstraction and assuming the abstraction cannot be wrong.

In this case, a single configuration detail sat between a normal-looking training process and a run whose optimization behavior was not what I intended.

The four hours I lost debugging it were painful, but the experiment changed the way I approach ML problems. I now spend less time randomly changing plausible things and more time designing small tests that can separate one explanation from another.

That lesson is probably more valuable to me than the 19-hour run itself.

Quick technical answers

Why can training loss be much higher than validation loss in Hugging Face Trainer?

There are legitimate reasons for train and validation loss to differ, but in my NLLB-200 experiment the unusually large gap was caused by incorrect loss scaling associated with gradient accumulation. The key clue was that reported loss increased almost linearly as gradient_accumulation_steps increased.

How did I identify gradient accumulation as the cause?

I held the model and data constant and changed only gradient_accumulation_steps. Reported loss went from 3.24 at accumulation 1 to 25.92 at accumulation 8—almost exactly an 8× increase.

What fixed the NLLB Trainer loss-scaling problem in my run?

I set trainer.model_accepts_loss_kwargs = False. Training loss changed from 24.26 to 3.03 and gradient norm from 0.234 to 0.030. Current Hugging Face documentation also advises setting this flag to false when the loss does not use num_items_in_batch.

Does every NLLB training run need this line?

No. Transformers evolves, and the correct behavior depends on the version and training path being used. This article documents the issue I encountered. For a new run, reproduce the behavior on your installed version and check the current Trainer documentation rather than applying a workaround blindly.
