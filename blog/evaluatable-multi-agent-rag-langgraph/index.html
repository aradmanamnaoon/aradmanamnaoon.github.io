How to Design an Evaluatable Multi-Agent RAG System with LangGraph

Adding more agents does not automatically make a research assistant more reliable. A better starting point is a workflow with explicit responsibilities, inspectable evidence, bounded revision, and an evaluation set that can expose regressions.

By Seyyed Arad Hosseini Moghaddam October 3, 2026 12 min read

  3. Treat evidence as part of the output

Retrieval-augmented generation (RAG) gives a language model access to information outside its parameterized knowledge by retrieving external passages and using them during generation. That is a useful foundation for research assistants, but a production-shaped assistant has more jobs than retrieval and answer generation: it must interpret the request, choose tools, handle missing evidence, synthesize sources, and communicate uncertainty.

A multi-agent workflow can make those responsibilities easier to inspect. It can also add latency, cost, and more places for errors to accumulate. The design goal should therefore be a workflow whose decisions can be inspected and measured, not the largest possible collection of agents.

This article draws on the public AI Research Assistant Platform project in my portfolio. The project describes a LangGraph workflow with planner, retrieval, research, tool execution, synthesis, and reflection responsibilities, alongside ChromaDB retrieval, SQLite persistence, LangSmith tracing and evaluation, and FastAPI REST and SSE interfaces. The architecture below explains the design choices and evaluation approach; it does not claim that one workflow is right for every application.

Why structure matters in RAG

The original RAG formulation combines a language model’s parametric memory with a non-parametric memory that can be searched at inference time. In an application, that retrieval step is only useful when the retrieved material is relevant to the question and the generated answer stays grounded in it.

A simple retrieve-then-generate chain can work well for a narrow question over a small corpus. Research questions often need something more: a query may need decomposition, multiple search routes, tool use, and a final answer that reconciles evidence. A graph lets those transitions become explicit. Each node has a job, and the state passed between nodes can record what was requested, what was retrieved, what tools returned, and what the final response needs to contain.

This structure helps debugging. If a response is weak, you can ask whether the planner selected the wrong route, retrieval returned poor passages, a tool failed, or synthesis overstated the evidence. Without observable intermediate state, all of those failures appear as “the model gave a bad answer.”

A workflow with explicit responsibilities

A practical research workflow can begin with a planner that classifies the task and creates a small work plan. Based on that plan, it can route the request to one or more focused branches. For example, a question about a project can use repository or portfolio context, while a literature question may require search and source review. 

Question
   ↓
Planner ──→ clarify or answer directly
   ↓
Research branches: retrieval · web research · tools
   ↓
Evidence-aware synthesis
   ↓
Quality check ──→ answer / bounded revision

The branches do not all need to run for every request. Routing should be based on the user’s task and the tools available to the application. When two branches are independent, a graph can schedule them in parallel; when one branch depends on another’s result, the dependency should be explicit. This avoids running expensive steps without a reason and makes the workflow easier to reason about.

Define a shared state contract

Before adding nodes, decide what information moves through the graph. A useful state contract can include the original question, a normalized query, a list of planned tasks, retrieved passages with source identifiers, tool results, a draft answer, quality-check notes, and the final answer. Keep source metadata attached to each passage so later nodes do not have to reconstruct where a claim came from.

State should record evidence and control flow, not just accumulate every message produced along the way. Smaller, named fields make traces easier to inspect and reduce the risk that a downstream node mistakes an intermediate thought for verified evidence.

Keep node inputs and outputs narrow

A retrieval node should return passages and metadata. A search node should return source records. A synthesis node should receive the question and selected evidence, then produce an answer whose factual claims can be connected to that evidence. Narrow interfaces make it clearer which component needs attention when results are poor.

Treat evidence as part of the output

A bibliography at the end of an answer is not enough to establish that individual claims are supported. Preserve source identifiers through retrieval and synthesis, then ask the answer generator to associate material claims with the supporting source. This lets a reviewer follow the path from question to passage to response.

Retrieval quality and answer quality are separate concerns. A relevant passage can be retrieved but ignored; an answer can sound plausible even when retrieval returned weak evidence. During evaluation, inspect retrieval and generation separately. For retrieval, check whether useful sources appear in the result set. For generation, check whether the answer uses those sources accurately and avoids unsupported details.

When the evidence is incomplete, the system should be allowed to say so. A good answer can identify what it found, what remains uncertain, and which additional information would help. That is more useful than forcing a confident conclusion from a thin evidence set.

Keep reflection bounded

A quality-check step can catch missing citations, unanswered parts of a request, or a mismatch between the draft and the retrieved evidence. It can then either accept the draft or request a limited revision. Reflection is most useful when the checker has concrete criteria and a clear stopping condition.

Unbounded self-critique can turn into repeated rewriting without measurable improvement. Set a maximum number of revisions, record why each revision was requested, and return the best valid response when the limit is reached. A checker should not simply ask a second model whether the first model “looks good”; it should inspect specific properties such as coverage, citation presence, citation support, and required output format.

LangGraph’s persistence and checkpointing capabilities are useful when a workflow needs to preserve state across steps or resume after interruption. They are especially relevant when a system includes human review or long-running tasks. Persistence does not make a workflow correct by itself; it gives the application a way to preserve and inspect its execution state.

Evaluate the system in layers

“The answer seems good” is not a repeatable evaluation method. Build a small, representative dataset of questions and expected behavior. Include questions answerable from the available sources, questions with incomplete evidence, multi-part questions, and cases that should trigger a tool or route.

Then evaluate distinct parts of the workflow:

  • Routing: Did the planner choose an appropriate path and avoid unnecessary tools?
  • Retrieval: Did the returned passages contain the relevant information and useful source metadata?
  • Tool execution: Did the tool succeed, return usable output, and surface errors clearly?
  • Grounding: Are important factual claims supported by the cited evidence?
  • Coverage: Did the response address every part of the request?
  • Behavior: Did the system acknowledge gaps instead of inventing an answer?

Use deterministic checks where possible. For example, code can check that every source identifier in the answer exists in the retrieved-source set, or that a required structured field is present. For qualities that need judgment, use human review or a carefully designed model-based evaluator and periodically compare its decisions with human labels.

Run the same examples against each meaningful workflow change. LangSmith supports evaluation against datasets and comparison across application versions; whichever tool you choose, keep the examples and criteria stable enough to reveal regressions. A trace is useful for explaining one run, while a dataset helps determine whether a change improved the system across a range of cases.

Keep latency and cost visible alongside quality. A revision loop might improve some answers while adding another model call to every request. Measure the tradeoff before enabling it broadly.

Failure modes to test

Good answer, wrong route

A model may produce a plausible response from general knowledge without using the project corpus or research tool that the question required. Add tests that verify both answer quality and route selection.

Relevant sources, unsupported synthesis

Retrieved material can be relevant while the final answer adds claims not found in it. Check citation support at the claim level, not only whether the answer contains links.

Tool errors hidden by the final response

A failed search or API request should be visible in the trace and reflected in the final answer when it affects coverage. Test timeout and empty-result cases deliberately.

Revision loops that add cost without value

A reflection step can repeat without changing the evidence or resolving the identified issue. Set a revision limit and compare quality and cost with the version that skips reflection.

Stale assumptions about the source corpus

Retrieval depends on the data that has actually been indexed. Test missing, outdated, and conflicting documents, and expose source dates or identifiers when they affect interpretation.

Practical takeaways

  1. Start with the user task and define the smallest workflow that can handle it.
  2. Give each node a narrow responsibility and explicit inputs and outputs.
  3. Keep source identifiers and metadata attached to retrieved evidence.
  4. Make missing evidence and tool failures visible instead of hiding them.
  5. Bound revision loops and measure their quality, latency, and cost.
  6. Use representative evaluation examples to compare workflow versions.
