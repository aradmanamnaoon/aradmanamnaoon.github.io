Securing MCP Servers: A Practical Developer Guide

Model Context Protocol makes tools easier to connect to agents. That makes the server boundary more important: every tool call still needs ordinary authorization, validation, and operational controls.

By ARADMANAMNAOON October 6, 2026 ~10 min read Updated for the MCP security guidance available on October 6, 2026
Quick answer Treat every MCP server as a privileged API boundary. Give each tool only the access it needs, enforce authorization and input checks inside the server, validate outputs before they return to the model, isolate local processes, and require action-specific approval for consequential operations. MCP standardizes communication; it does not make a tool safe by itself.

In this guide

Connecting an agent to a calendar, repository, database, or internal API can take only a few lines of code. The hard part is deciding what that connection is allowed to do—and making sure those limits remain effective when a model sees untrusted content or when a server changes.

Model Context Protocol (MCP) gives clients and servers a shared way to expose tools, resources, and prompts. It does not replace application security. The model can choose a tool and produce its arguments, but trusted code must still decide whether the call is allowed and safe to execute.

Start with the trust boundary

A useful mental model is: the host presents the experience, the client connects to a server, and the server performs work against an API, file system, or other resource. Each server is a separate dependency with its own code, credentials, permissions, and failure modes.

That means the threat model includes more than malicious users. A tool description can be changed, a tool response can contain prompt injection, a compromised package can run locally with the user's privileges, and a server can accidentally exercise broader credentials than the person who asked for the action.

Security rule: Treat model output, tool arguments, tool descriptions, remote content, and tool results as untrusted input. The authorization decision belongs in ordinary application code at the point where the action happens.

Keep a simple inventory for each server: who publishes it, where it runs, what data it can reach, which identity it uses, which tools it exposes, and which actions can change state. If you cannot answer those questions, do not give the server production credentials yet.

Keep tools and credentials narrow

Design tools around one clear job. A read_project_file operation with a restricted project root is easier to reason about than a general-purpose shell tool. A read-only reporting credential is easier to contain than a database administrator token.

  • Expose only the tools needed for the agent's task. Separate read operations from write or administrative operations.
  • Scope credentials to a single server and a small set of resources. Prefer short-lived credentials when the provider supports them.
  • Enforce authorization for the current user and resource on every call. Do not rely on a model remembering a policy prompt.
  • Place high-impact actions behind a separate, explicit approval step. Show the exact operation and its material parameters.
  • Set request, token, retry, time, and rate limits so a loop cannot spend indefinitely or overwhelm a dependency.

A tool schema can constrain the shape of arguments, but a valid shape does not imply permission. For example, a syntactically valid account_id still needs to be checked against the authenticated user's access on the server.

Validate both directions

Tool arguments often originate from model output influenced by user text, retrieved documents, or web pages. Validate them as you would validate input to any public API. Use strict schemas, reject unknown fields when appropriate, set length and range limits, and apply domain rules before touching a database, file, or service.

async function updateTicket(actor, input) {
  const args = UpdateTicketSchema.parse(input);
  await authorization.requireCanEditTicket(actor, args.ticketId);
  if (!ALLOWED_STATUSES.has(args.status)) {
    throw new Error("Unsupported status");
  }
  return tickets.update(args.ticketId, { status: args.status });
}

This example keeps parsing, authorization, and the side effect together. The model never gets to choose which authorization rule applies. In a real implementation, return a clear, bounded error and avoid including secrets or internal details in the response.

Validation also applies to tool results. A result may be fed into the model or passed to another tool. Normalize output to the fields needed for the task, impose size limits, and label retrieved content as data rather than trusted instructions. Do not treat a trusted server as proof that every returned string is safe.

For tools that fetch URLs, do not let an LLM-selected destination become an unrestricted server-side request. Use an allowlist or a constrained destination policy, validate redirects and resolved addresses, and block private or metadata-service ranges where the threat model requires it. This is a common way prompt injection can turn a seemingly harmless fetch tool into an SSRF path.

Get authorization and network boundaries right

For remote HTTP servers, use the current MCP authorization profile and the OAuth protections it specifies. A server should accept access tokens intended for that server, verify the relevant claims, and authorize each protected request. Do not forward a token meant for the MCP server to a different upstream API as a shortcut; obtain and use credentials appropriate for the upstream service.

Authentication answers “who is calling?” Authorization answers “may this caller perform this operation on this resource?” A successful login does not answer the second question. Keep authorization checks close to each protected operation, including when a call carries a workflow ID or other state handle.

  • Use HTTPS for remote connections and validate the server identity.
  • Check the expected audience for tokens; never treat possession of a token or opaque handle as proof of permission.
  • Validate incoming request origins and hosts according to the transport guidance, and bind local HTTP listeners to loopback unless remote access is intentional.
  • Apply quotas, timeouts, and rate limits by user or tenant.
  • Store credentials in a secure secret store rather than plaintext configuration or logs.

Transport checks and tool checks solve different problems. A correct origin header does not authorize a database query, and a valid OAuth token does not make an arbitrary URL safe to fetch.

Isolate local servers and review changes

A local server often runs as a child process with the same operating-system permissions as its client. The stdio transport avoids exposing a listening network endpoint, but it does not sandbox the process or limit its file, network, or credential access.

Run local servers with the least operating-system privilege available. Restrict readable and writable directories, limit network egress, avoid arbitrary shell execution, pin and review dependencies, and inspect the exact startup command before running it. For remote servers, isolate credentials and data from other servers rather than assuming that tools share a safe trust boundary.

Tool definitions are part of the interface the model sees. Review names, descriptions, parameter schemas, and output schemas before enabling a server. Keep a reviewed snapshot or equivalent change detection, and require re-review when those definitions change. This can catch metadata changes; it does not prove that the code behind an unchanged definition is trustworthy.

Finally, log enough to reconstruct what happened: server identity, tool name, actor, timestamp, outcome, and a safe representation of relevant parameters. Redact secrets and personal data. Test prompt-injection cases, cross-user access, malformed arguments, retries, and failure handling in a controlled environment before deployment.

A deployment checklist

  • Every server has an owner, source, version, and documented data boundary.
  • Every tool has a narrow purpose, strict input schema, and server-side authorization.
  • Read and write permissions use separate tools or credentials where practical.
  • Remote tokens are audience-checked, scoped, protected in storage, and never passed through to unrelated APIs.
  • URL-fetching tools have SSRF defenses and do not follow unrestricted redirects.
  • Local processes run with restricted file-system and network access.
  • High-impact actions require approval tied to the exact action and parameters.
  • Tool outputs are bounded, normalized, and treated as untrusted content.
  • Rate, time, retry, and cost limits are configured and monitored.
  • Security tests cover tool changes, prompt injection, tenant isolation, and denied actions.

Start with one read-only server and a small evaluation set. Add write access only after you can show which trusted checks prevent unauthorized actions, how failures are contained, and how a reviewer can understand a tool call before it executes.

Frequently asked questions

Does MCP provide security automatically?

No. MCP defines a communication protocol and security guidance, but deployments still need authentication where appropriate, per-tool authorization, input and output validation, isolation, and operational controls.

Is stdio safer than HTTP for local MCP servers?

Stdio avoids opening an HTTP listener, which can reduce network exposure. It does not limit what the local process can read, change, or send over the network. Use OS-level restrictions and a reviewed startup command.

Are tool descriptions and schemas security controls?

They help a host and model understand the interface, but they do not enforce permission. Enforce authorization in trusted server code, and review tool metadata for unexpected changes.

What is token passthrough?

It is accepting a token presented to an MCP server and forwarding it to another service without validating that the token was issued for the MCP server and is appropriate for that downstream use. Follow the current authorization specification and use credentials intended for each resource.

How should an agent handle a sensitive tool call?

Use a trusted approval step that displays the specific action and parameters, binds approval to the current actor and request, and rechecks authorization at execution time. Do not let model text act as the approval signal.
